# 7 · Security — Threat Defense and Threat Intelligence

About half of Infoblox's growth story is selling DNS-layer security to existing DDI customers. Threat Defense is the product; **TIDE** (Threat Intelligence Data Exchange) and **Zero-Day DNS** are the data engines behind it. Expect a deep-dive on either the security model or the threat-intel pipeline.

## 7.1 Why DNS is a useful security control point

- Almost every connection starts with a DNS query. Blocking at DNS stops connections before they're attempted.
- DNS is high-volume but low-bandwidth — easy to inspect every query without performance impact.
- Malware C2, phishing kits, data exfiltration, and DGA traffic all leave a DNS fingerprint.
- DNS sees lateral and outbound flows that firewalls might miss (intra-VPC, BYOD, roaming users).

The downsides:
- DNS-over-HTTPS in apps bypasses corporate DNS unless you intercept it.
- IP-only traffic (no name lookup) bypasses DNS-layer policy.
- Encrypted SNI eventually makes name-based inspection harder downstream.

## 7.2 Threat Defense — the product

Threat Defense is a managed recursive-resolver service plus a policy engine plus threat intel. Three deployment shapes:

1. **SaaS-only** — customer points endpoints at Infoblox's anycast recursive resolvers. All policy and intel runs in the cloud.
2. **On-prem appliance / NIOS-X** — local recursive resolver enriched with Infoblox intel feeds (RPZ zones, blocklists, lookup APIs).
3. **Hybrid** — local first-hop resolver (low latency, offline-safe), but escalation/lookups/reporting all cloud-coordinated.

Decision logic on every query:

```
query "evil.example"
  |
  v
[policy lookup against blocklist trie] ----> hit? -> NXDOMAIN / redirect / walled-garden + alert
  |
  v (miss)
[behavioral / ML check] ---> high score? -> sinkhole + alert
  |
  v
[normal recursive resolution]
```

Behavioral checks happen asynchronously for many of them — the query is answered fast, and an event is published for offline analysis that may produce a new blocklist entry.

## 7.3 Threat intel — what gets blocked

Infoblox's threat-intel catalog is broad:

- **Known-bad domains** — malware C2, phishing, ransomware download sites.
- **Newly-registered domains** — domains registered in the last 24–72 hours, often pre-emptively flagged.
- **DGA domains** — generated by malware families; classified via ML on lexical features.
- **Lookalike / typosquatting** — `paypa1.com`, `app1e.com` proximity to high-value brands.
- **DNS-tunnel indicators** — anomalous query patterns from a single endpoint.
- **C2 infrastructure** — domains that resolve to IP ranges historically used for C2, hosted on known-bad ASNs.

The differentiator Infoblox claims: their **passive DNS** corpus is huge (every Infoblox-customer resolver feeds it, anonymized), so they see new domains being used before public blocklists pick them up.

## 7.4 TIDE — Threat Intelligence Data Exchange

TIDE is the API/data-distribution layer for Infoblox's threat intel.

- **Input feeds**: Infoblox's own research team, partner feeds, customer-submitted indicators (STIX/TAXII format), automated detection from the global query stream.
- **Normalization**: convert all indicators to a common schema — `(type, value, severity, confidence, first_seen, expires_at, threat_class, source)`.
- **Distribution**: REST API for fetching by type/source, Kafka topics for streaming subscribers, RPZ zone feeds for DNS servers that consume RPZ directly.
- **Confidence tiering**: not every indicator is "block" — high-confidence ones block, medium ones alert, low ones are observed.

From a data-engineering standpoint, TIDE is a curated, deduplicated, expiring, multi-source IOC store with high write throughput (research + ML pipeline) and very high read throughput (every Threat Defense customer fetching feeds).

## 7.5 Zero-Day DNS

The signature feature: detect malicious infrastructure before any human classifies it.

Concept: an attacker registers a domain, sets up infrastructure, then launches a phishing campaign minutes-to-hours later. Static blocklists update too slowly. 
Infoblox watches:

- Newly observed domains (never seen in any DNS query before).
- Domain registration events (via partnerships with registries).
- Resolution behavior (does the new domain resolve? to what IPs? are those IPs near known-bad IPs?).
- Query velocity (a sudden spike of queries to a brand-new domain from many tenants = campaign).
- Lexical features (typosquatting score against high-value brands).

ML model scores the domain; high scores get auto-blocked across the customer base with operator review.

Latency target: **minutes** from first sighting to global block.

## 7.6 The streaming pipeline

```

                                     |
                                     v

                                     |
                       +-------------+-----+-----+----------+
                       |                   |     |          |
                       v                   v     v          v
                  Aggregations         DGA ML  Tunnel ML   Newly-
                  per (tenant,         scorer  detector    seen-
                  domain, time)                            domain
                                                           tracker
                       |                   |     |          |
                       +-----+--------+----+-----+----------+
                             |
                             v
                       Decisioning service
                             |
                             v
                        TIDE update
                             |
                             v
                  Push to every NIOS-X / PoP
```

Throughput estimates (back-of-envelope):
- 10 billion queries/day = ~115K QPS average, ~500K QPS peak across the fleet.
- Each event ~200 bytes = ~25 MB/sec ingest.
- Stored compressed for 90 days = single-digit PBs.
- Compute: a Flink job per detector, possibly per-tenant where required.

## 7.7 RPZ — Response Policy Zones

Standardized format (RFC-draft, widely supported in BIND, Knot, Unbound) for distributing DNS policy.

An RPZ is a "fake" DNS zone whose records express rules:

```
malware.example.com  CNAME .                      ; NXDOMAIN
phishing.example.com CNAME walled-garden.corp.   ; redirect
*.dga-family-x       CNAME .
```

Recursive resolvers load RPZs and consult them before answering. Updates propagate via standard zone transfer (IXFR with TSIG).

Infoblox publishes RPZ feeds that any RPZ-capable resolver can consume — but you get richer features (logging, walled garden, behavioral) by running their resolver.

## 7.8 SOC Insights

The analytics layer over Threat Defense. Correlates:
- DNS events.
- Asset inventory (Universal Asset Insights).
- Network flow / endpoint data (via integrations with EDR, SIEM, etc.).

Outputs:
- **Insights** — clusters of related events that look like a single incident.
- **Risk scoring** for users/devices/assets.
- **Recommended actions** — quarantine, investigate, escalate.

Underneath: graph database + ML correlation models + a queue of human-analyst-curated rules.

## 7.9 Integrations

Threat Defense is meant to fit into a SOC's stack:
- **SIEM** (Splunk, QRadar, Sumo, etc.) via syslog / HTTP event collector.
- **SOAR** (Cortex XSOAR, Splunk SOAR) via REST.
- **EDR** (CrowdStrike, SentinelOne) — Infoblox can quarantine an endpoint by name if the EDR is integrated.
- **Firewall / NAC** — push block actions.
- **ITSM** (ServiceNow) — auto-create tickets.

A staff-level question: "How do you design the integration layer? What's the contract you give partners?" Answer: webhook ingress (signed/verified), a normalized event schema (think CEF or OCSF), backpressure, replay capability, partner-version skew tolerance.

## 7.10 Performance and reliability constraints

DNS is in the hot path. The security check cannot add appreciable latency to the user experience.

Targets:
- p99 added latency: **< 5 ms** for policy check.
- Availability: **99.99%+** for the recursive resolver itself (matched by anycast PoP redundancy).
- Cache-hit ratios at the PoP: 80%+ — most queries don't even need policy check freshness because the cached answer already incorporates policy.

The blocklist data structure has to be very fast and memory-compact:
- A bloom filter for "definitely not in list" pre-check.
- A trie/hash for full lookups when the bloom says "maybe".
- Per-tenant overrides applied on top.

## 7.11 Privacy and compliance

A DNS-security product sees every query a user makes — including healthcare lookups, banking, etc. Privacy is non-negotiable.

- Customer queries are processed by tenant; data isolation is strict.
- Anonymization / aggregation for the global threat-intel corpus (you contribute aggregate signals, not your queries).
- Per-region data residency (EU customers can pin to EU PoPs for GDPR).
- SOC 2, FedRAMP, ISO 27001 controls.
- Audit log of every administrative action.

If asked: "How would you design this so a customer can prove to their auditor that their queries aren't visible to other tenants?" — 
talk encryption-at-rest with tenant-specific KMS keys, row-level security in the analytics store, network segmentation in the processing tier, signed audit logs.

## 7.12 Worked design problem — newly-registered-domain detector

**Prompt**: design a service that detects and blocks newly-registered malicious domains within 5 minutes of first being queried in the customer fleet.

**Sketch**:

- **Input**: real-time query event stream (Kafka topic), partitioned by hash of `qname`.
- **State**: a Redis-backed (or RocksDB-embedded) set of "domains seen ever" — bloom filter front-end, exact set behind.
- **Hot path**: each event → check bloom → if "maybe new", check exact set → if truly new, emit `NEW_DOMAIN_OBSERVED` event.
- **Enrichment**: parallel job pulls registration data (RDAP) and ML features (lexical, ASN of resolved IP, registrar reputation).
- **Decisioning**: stream processor accumulates enrichment + observation count and decides if score > threshold.
- **Block path**: TIDE entry created → pushed to all NIOS-X via mTLS gRPC + Kafka topic → enforced on next query.
- **SLA**: target p95 < 5 min observation-to-block. Bottleneck: RDAP lookup (rate-limited by registries) — cache aggressively, batch by registry.
- **Scale**: 10B queries/day, most are not new; the new-domain rate is ~10s of millions/day at most. Manageable.
- **Failure modes**:
  - Bloom false positives → wasted exact lookups; tune size.
  - RDAP outage → degrade to lexical-only scoring.
  - Decisioning service down → existing TIDE entries still in effect; new blocks delayed.

## 7.13 Must-internalize

- DNS is the cheap, ubiquitous security control point — most threats *use* DNS.
- Threat Defense = recursive resolver + policy engine + threat intel feeds.
- TIDE = the IOC distribution platform; RPZ is one delivery format.
- Zero-Day DNS = ML on newly seen domains; aims for minute-class latency.
- Pipeline: Kafka → Flink/Spark → ClickHouse → decisioning → TIDE → fleet.
- Hot-path policy check budget: <5 ms p99.
- Privacy/compliance: tenant isolation, anonymized aggregates, regional residency.
